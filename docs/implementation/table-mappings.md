# Table mappings

WALlaby requires each persisted flow to contain a versioned table-mapping policy. The policy selects source relations and columns, maps their destination names, and sets each table's write behavior.

Existing flows without `config.table_mappings` are incompatible. Recreate them or reconfigure them with a mapping generated by `wallaby-admin`. WALlaby does not import or infer an old flow configuration.

The CLI can read a local mapping file, but it expands the file before it sends the flow to the API. WALlaby persists only the expanded mapping. The server and workers never read a persisted local path.

## Contract

```yaml
version: 1
destinations:
  - destination: warehouse
    future_tables:
      action: include
      target_schema: "{schema}"
      target_table: "{table}"
      future_columns:
        action: include
        target_column: "{column}"
      write:
        mode: append
    tables:
      - source_schema: public
        source_table: customers
        action: include
        target_schema: analytics
        target_table: accounts
        future_columns:
          action: include
          target_column: "{column}"
        columns:
          - source_column: id
            action: include
            target_column: account_id
          - source_column: secret
            action: exclude
        write:
          mode: upsert
          key_columns: [id]
          watermark_column: updated_at
```

Each flow destination has exactly one mapping set. Exact table rules override `future_tables`. Exact column rules override `future_columns`. Every action must explicitly use `include` or `exclude`.

The generated future policy includes new tables and columns with their source names. New tables use append mode because their key contract is unknown. Current tables with a primary key use upsert by default. Current tables without a primary key use append by default.

Future templates preserve each identifier component independently. Future `target_schema` must contain exactly one `{schema}` and no other placeholder. Future `target_table` must contain exactly one `{table}` and no other placeholder. Future `target_column` must contain exactly one `{column}` and no other placeholder. Fixed prefixes and suffixes remain valid, for example `raw_{schema}`, `tbl_{table}`, and `dst_{column}`. Cross-variable or duplicate forms such as `{schema}_{table}` and `{table}_{table}` are invalid. This keeps ambiguous-looking source pairs such as `a.b_c` and `a_b.c` distinct. Exact table and column target identifiers remain unrestricted literal identifiers without templates. Exact target names do not support templates. Identifier matching and output preserve source case. Leading or trailing whitespace in destination, table, column, key, watermark, or template identifiers is invalid rather than normalized.

## Write behavior

`append` writes every source event. A table can use append even when the source has a primary key. WALlaby adds `__wallaby_operation`, `__wallaby_deleted`, and `__wallaby_source_position`. The source position comes from the record or the canonical batch or transaction checkpoint. WALlaby fails if no stable source position exists.

`upsert` requires a nonempty ordered `key_columns` list. These configured columns are the authoritative explicit match identity; runtime does not reinterpret or compare them with source primary-key metadata. The future catalog-based CLI generator will populate `key_columns` from catalog primary keys by default, but the persisted list remains authoritative. A configured-key update fails closed unless WALlaby can reconstruct the old match key from the before image or source record key; otherwise the old target row could be left behind.

`watermark_column` is optional. It must exist in the source schema and remain included by the projection. It identifies the incoming row's freshness and does not identify the row. A watermark upsert therefore still requires `key_columns`. The destination applies a mutation only when the incoming watermark is newer than the stored watermark. Append mode does not suppress events based on the watermark.

Iceberg and other append-only destinations reject upsert mappings. Iceberg row-level mutation needs a separate equality-delete or merge-on-read durability protocol.

## Projection rules

WALlaby projects the schema, table, columns, row images, unchanged-column list, record key, and structured DDL as one logical operation. Excluded-only transactions still advance the checkpoint.

A nonidentity projection rejects raw WAL payload mode because opaque payload bytes can retain excluded names and values. WALlaby clears opaque payload bytes when it changes a logical record.

Raw SQL DDL cannot be renamed safely. A nonidentity projection requires a structured DDL plan and fails closed on raw SQL. WALlaby filters DDL for excluded objects and maps included table and column names.

WALlaby preserves source relation and column IDs in metadata. It does not rewrite generated-column expressions. Rename or filtering that would require expression rewriting fails unless the generated column is excluded.

Changing a mapping changes the destination configuration fingerprint and creates a new flow incarnation. A running or stopping flow cannot change mappings.
