# Table mappings

WALlaby requires each persisted flow to contain a versioned table-mapping policy. The policy selects source relations and columns, maps their destination names, and sets each table's write behavior.

Existing flows without `config.table_mappings` are incompatible. Recreate them or reconfigure them with a mapping generated by `wallaby-admin`. WALlaby does not import or infer an old flow configuration.

The CLI can read a local mapping file, but it expands the file before it sends the flow to the API. WALlaby persists only the expanded mapping. The server and workers never read a persisted local path.

## Contract

```yaml
version: 2
destinations:
  - destination: warehouse
    future_tables:
      action: include
      target_schema: "{{ .Schema }}"
      target_table: "{{ .Table }}"
      future_columns:
        action: include
        target_column: "{{ .Column }}"
      write:
        mode: append
    tables:
      - source_schema: public
        source_table: customers
        action: include
        target_schema: analytics
        target_table: accounts
        future_columns:
          action: include
          target_column: "{{ .Column }}"
        columns:
          - source_column: id
            action: include
            target_column: account_id
          - source_column: secret
            action: exclude
          # Prevent future source account_id from also mapping to target account_id.
          - source_column: account_id
            action: exclude
        write:
          mode: upsert
          key_columns: [id]
          watermark_column: updated_at
      # Prevent a future analytics.accounts source from reusing this exact target.
      - source_schema: analytics
        source_table: accounts
        action: exclude
```

Each flow destination has exactly one mapping set. Exact table rules override `future_tables`. Exact column rules override `future_columns`. Every action must explicitly use `include` or `exclude`.

The generated future policy includes new tables and columns with their source names. New tables use append mode because their key contract is unknown. The generator retains ordered source-primary-key identity, while the CLI admits its default per exact destination/profile: capable destinations use upsert for current primary-key tables and append-only destinations automatically use append. Current keyless tables use append. Explicit per-table write-mode overrides can select append, or request upsert only when keys and the exact destination/profile capability allow it. The exact managed Snowflake SQL profile is narrower: selection must contain exactly one relation with a complete ordered source primary key; generation emits only that upsert relation and excludes future tables. It rejects append, watermark, multi-relation, keyless, and nonexact match-column overrides before output.

Version 2 future templates preserve each identifier component independently through a deliberately restricted Go `text/template` AST. Future `target_schema` must contain exactly one `{{ .Schema }}` field action, future `target_table` exactly one `{{ .Table }}`, and future `target_column` exactly one `{{ .Column }}`. Fixed literal prefixes and suffixes remain valid, for example `raw_{{ .Schema }}`, `tbl_{{ .Table }}`, and `dst_{{ .Column }}`. WALlaby executes the compiled template once with typed `Data{Schema, Table, Column string}`; injected bytes are copied unchanged and are never recursively interpreted. Cross-field or duplicate actions, nested fields, chains, literals, declarations, conditions, loops, functions, pipelines, variables, and template definitions or includes are invalid. Gomplate functions and datasources, Sprig, environment variables, and file or network access are unsupported. This keeps ambiguous-looking source pairs such as `a.b_c` and `a_b.c` distinct. Validation inverses every exact target through the applicable future template and rejects exact/future relation or column collisions unless the inverse source has an explicit include or exclude override. Exact table and column target identifiers remain literal: executable Go-template actions are rejected, but arbitrary single braces are preserved. Identifier matching and output preserve source case, dots, quotes, Unicode, and quoted-identifier whitespace. Mapping template strings themselves may not have outer whitespace.

## Write behavior

`append` writes every source event. A table can use append even when the source has a primary key. WALlaby strips source `primary_key`, `primary_key_ordinal`, and `replica_identity` metadata from the projected target schema, so generated target DDL and managed target admission cannot impose source-key uniqueness on an event log. WALlaby adds `__wallaby_operation`, `__wallaby_deleted`, and `__wallaby_source_position`. The source position comes from the record or the canonical batch or transaction checkpoint. WALlaby fails if no stable source position exists.

`upsert` requires a nonempty ordered `key_columns` list. These configured columns are the authoritative explicit match identity; runtime does not reinterpret or compare them with source primary-key metadata. Every configured key must be available in PostgreSQL replica identity or a `REPLICA IDENTITY FULL` old-row image. Managed PostgreSQL requires an immediate, valid target primary-key or unique constraint over exactly the projected policy keys in policy order, and emits `ON CONFLICT` in that same order. Source primary-key and replica-identity metadata never expands target uniqueness; under full replica identity the persisted policy still selects the only target match key. The catalog generator populates `key_columns` from catalog primary keys by default. Explicit match-column overrides replace that generated list, and the persisted ordered list remains authoritative. A configured-key update fails closed unless WALlaby can reconstruct the old match key from the before image or source record key; otherwise the old target row could be left behind.

`watermark_column` is optional and must name a selected real column. In append mode it is projected metadata only; it need not be nonnullable, orderable, or present in replica identity, and it never suppresses delivery. In watermark-guarded upsert it must be nonnullable, use an admitted orderable PostgreSQL type, and be present in replica identity or full old-row images so deletes carry it. An upsert watermark identifies freshness rather than row identity and therefore still requires `key_columns`.

PostgreSQL canonicalizes configured key values and watermark values through explicit projected PostgreSQL casts before state lookup. Unsupported key or watermark types fail before mutation. The hidden state table is schema-verified before use and is keyed by flow, target schema/table, mapping fingerprint, ordered key-column names, and canonical key values. Target DML and state advancement share one transaction and lock the state row. Greater watermarks advance. Equal watermarks advance only at a greater canonical PostgreSQL LSN. Equal watermark and LSN with identical content is idempotent; differing content is a delivery conflict. Deletes retain tombstones. Bootstrap publication atomically deletes the complete state scope for each target/projection/key policy and seeds exactly the published snapshot key set. Retry repeats that replacement from the published target, so old absent keys and tombstones cannot suppress later streaming reinsertion. Append mode treats a configured watermark as metadata and does not suppress events.

Iceberg and other append-only destinations reject upsert mappings. Iceberg row-level mutation needs a separate equality-delete or merge-on-read durability protocol.

PostgreSQL supports append, explicit-key upsert, and atomic durable-state watermark-guarded upsert. Generic Snowflake is append-only, but the named managed Snowflake SQL profile is current-state explicit-key upsert only: it rejects append and watermark policies, requires `future_tables.action: exclude`, and admits exactly one mapped relation whose `key_columns` exactly equal the complete ordered primary key in the unprojected managed source contract. Every primary-key component must survive projection, although mapped component names may change. Its ephemeral runtime contract is the projected target schema/hash; the persisted source contract remains unchanged. DuckDB, DuckLake, Snowpipe, ClickHouse, Iceberg, S3, Kafka, HTTP, gRPC, pgstream, and Redpanda are admitted only for append mappings. DuckDB and DuckLake do not claim upsert until insert-on-conflict behavior has dedicated connector evidence. Unsupported policies fail definition validation and are checked again against the constructed connector before it opens.

Endpoint options cannot alter logical selection, naming, write behavior, or projected event semantics. Named managed profiles retain only profile-specific physical ownership and transport options.

## Projection rules

WALlaby projects the schema, table, columns, row images, unchanged-column list, record key, and structured DDL as one logical operation. Excluded-only transactions still advance the checkpoint. A DDL source position projected to no executing destinations receives an explicit durable empty execution manifest and applied transition; WALlaby does not invent a destination receipt.

Mapped Iceberg materialization requires explicit `canonical_cdc_parquet_v2`. The sole Iceberg projector runs exactly once before canonical planning and hashing; PostgreSQL stream, publication, recovery, and consumer identities carry the projection version and mapping fingerprint. Iceberg consumes the mapped namespace, table, and columns directly and remains append-only. The historical `canonical_cdc_parquet_v1` bytes, schema documents, hashes, and object keys remain frozen. In v2 the canonical envelope solely owns `__wallaby_source_position`; append projection retains `__wallaby_operation` and `__wallaby_deleted` under explicit synthetic identity domains. Real field and Iceberg evolution identity includes source lineage, relation ID, and column ID, so renames retain identity while different lineages cannot alias.

Managed bootstrap consults mapping names before partition, primary-key, schema, and maximum-table eligibility checks. It freezes only included source tasks, queries those tasks with their source schemas, and delivers projected destination schemas, batches, and per-table write policies. Its manifest and receipts are bound to the mapping fingerprint.

Managed PostgreSQL creates receipt and bootstrap metadata objects only when absent. Every later open verifies exact ordered columns, types, nullability, defaults, generated/identity attributes, all constraints, and every index's method, keys, predicate/expression absence, opclasses, collations, options, and validity state. Authoritative bootstrap function signatures and bodies are exact. Generation stage retries also compare the complete stage column/default/index signature with the final target instead of trusting `CREATE TABLE IF NOT EXISTS`. A legacy, extra, or modified object fails closed; WALlaby does not run runtime `ALTER`, additive upgrade, or function-replacement compatibility paths.

A nonidentity projection rejects raw WAL payload mode because opaque payload bytes can retain excluded names and values. WALlaby clears opaque payload bytes when it changes a logical record.

Raw SQL DDL cannot be renamed safely. A nonidentity projection requires a structured DDL plan and fails closed on raw SQL. WALlaby filters DDL for excluded objects and maps included table and column names.

WALlaby preserves source relation and column IDs in metadata. It does not rewrite generated-column expressions. Rename or filtering that would require expression rewriting fails unless the generated column is excluded.

Changing a mapping or wire format changes flow incarnation identity; source and destination identity changes do as well. Unmanaged flows can apply those changes through the fenced reconfiguration RPC, which quiesces a running flow before installing the new incarnation. Managed flows reject both `UpdateFlow` and `ReconfigureFlow`, even for name or parallelism. Any managed change requires a distinct flow ID and new immutable destination/publication revision identities: stop the old flow, create and validate the replacement, start and verify it, cut consumers over, and delete or clean up the old flow only when safe. Terraform cannot orchestrate this managed cutover; any planned managed update fails with diagnostics and retains the existing state, so operators must model the replacement as a separate resource/revision. Only unmanaged name-only or parallelism-only changes use the ordinary update RPC. Append-mode watermarks remain projected metadata and never invoke freshness suppression or require watermark-guard capabilities. Primary-ACK outbox replay uses a PostgreSQL/SQLite-authoritative persisted monotonic replay order rather than timestamps, whose precision cannot establish fragment order.
